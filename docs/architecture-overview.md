# Архитектура конвейера: простейший MVP

Статус: согласованная база реализации. Этот документ заменяет расширенный проект «Трасса». Цель первой версии — воспроизводимый сквозной прогон «бизнес-требования → спецификация → web-приложение → проверки → отчёт» на двух разных задачах.

## 1. Что уже есть и что строим

В `main` есть каркас платформы: Angular + Taiga UI, FastAPI, SQLAlchemy/Alembic, PostgreSQL, Celery, Docker Compose, создание и редактирование проектов, фиксированный список этапов и техническая задача проверки очереди. Полноценного harness для агентов пока нет.

Harness в этом документе — общий исполнитель этапов: вызывает функцию этапа, предоставляет рабочую папку и LLM-шлюз, сохраняет артефакты и результат проверки, обновляет статус. Каждый участник пишет свою часть поверх этого каркаса.

| Слой | Стек и границы |
|---|---|
| Платформа | Angular 20.1.6 + Taiga UI 5, FastAPI, SQLAlchemy + Alembic, Celery, PostgreSQL 17.9, Docker Compose |
| Брокер Celery | Тот же PostgreSQL через Kombu SQLAlchemy transport: `sqla+postgresql+psycopg2://…`. Результаты Celery при необходимости — `db+postgresql+psycopg2://…` |
| Генерируемый MVP | Web: Angular + Angular Material, ASP.NET Core 10, PostgreSQL, Docker Compose. Один согласованный шаблон, расширяемый бизнес-правилами |
| Модель | Один настраиваемый endpoint и model ID через единый LLM-шлюз. Поддержку конкретных параметров проверяем на доступном сервере |

**Redis, RabbitMQ и Kafka не используем — ни в платформе, ни в первом генерируемом приложении.** PostgreSQL хранит состояние, события, вызовы модели и очередь. Android, PostGIS, событийная шина и дополнительные шаблонные модули — за пределами первой версии. Это осознанное сокращение охвата исходного кейса; готовность этих компонентов не заявляем.

Четыре сервиса платформы: `frontend`, `api`, `worker`, `postgres`. Один Celery worker с конкурентностью 1, одна очередь. Без Langfuse, отдельного CLI-продукта, визуального конструктора DAG и дополнительных брокеров.

## 2. Исполнение и этапы

Используем фиксированную последовательность, а не универсальный DAG-планировщик:

```text
analysis → spec → ui → scaffold → tests → develop → verify → report
```

| Ключ | Ответственный | Вход | Выход |
|---|---|---|---|
| `analysis` | Саня | Бизнес-требования | `analysis.json`: требования, роли, правила, критерии приёмки, допущения |
| `spec` | Саня | Анализ | `app.json`: сущности, поля, операции, бизнес-хуки, связи с критериями |
| `ui` | Артём | Анализ и спецификация | `ui.json`: экраны, действия, состояния и проходы пользователя |
| `scaffold` | Иван | Спецификация и UI | `product/`: собираемый каркас, контракты хуков, инфраструктура |
| `tests` | Тимофей | Критерии и публичные контракты | Приёмочные тесты; отчёт о проверке их способности находить ошибки |
| `develop` | Иван | Каркас, правила и неизменяемые тесты | Реализации хуков и ограниченных расширений |
| `verify` | Тимофей | Приложение и тесты | `verification.json`: результаты сборки, тестов, запуска и smoke |
| `report` | Тимофей | Статусы, допущения, проверки и метрики | `report.md` и `report.json` с фактическим результатом |

Максим делает harness, API запусков и шлюз модели. Артём также дорабатывает Студию для запуска, просмотра состояния и артефактов. Подробные персональные задания оформляются отдельными файлами.

Первый упавший этап останавливает основную последовательность. `report` запускается и при успехе, и при ошибке, если рабочая папка доступна. Успешный отчёт не превращает неуспешный прогон в успешный. Нет реализации — в отчёте «не реализовано»; нет проверки — «не проверено».

## 3. Граница этапа: обычная Python-функция

Этап не знает про HTTP, Celery и таблицы платформы. Его публичный интерфейс:

```python
execute(data: dict, workspace: Path, llm: Callable[..., dict]) -> dict
```

`data` содержит `run_id`, исходные `requirements`, словарь доступных входных `artifacts` (логическое имя → относительный путь). Для отчёта harness дополнительно передаёт снимок статусов и метрик. Результат содержит `artifacts` (имя → относительный путь созданного файла) и краткий `summary`.

- Файлы данных между этапами — JSON с `schema_version: 1`; человекочитаемый Markdown строится из них. Не поддерживаем одновременно JSON и YAML.
- Рабочая папка отдельная для каждого прогона. Все пути проверяются на выход из неё, включая симлинки. Входные артефакты предыдущих этапов не перезаписываются.
- Этап валидирует вход и выход. Некорректный вход — `ValueError`; невозможность выполнения — `RuntimeError` с понятным объяснением. Harness сохраняет ошибку и останавливает последовательность.
- Проверки этапов должны запускаться на локальных примерах с подставной функцией `llm`, без работающего harness и доступа к реальной модели.
- Итоговый интеграционный прогон обязательно выполняется с настоящей моделью: подставные ответы доказывают совместимость компонентов, но не качество генерации.

Спецификацию держим маленькой: требования и критерии со стабильными ID; сущности, типизированные поля, операции и хуки; экраны и действия. Без собственного универсального языка поведения и каталога десятков возможностей. Неподдерживаемое требование фиксируется как ограничение, а не скрывается генератором.

## 4. Состояние и восстановление

PostgreSQL — источник истины. Минимальные прикладные сущности: `runs`, `stage_runs`, `artifacts`, `events`, `llm_calls`. Существующий `Project` остаётся входной бизнес-задачей; у проекта может быть несколько прогонов. Старый список `Stage` из каркаса не используем как журнал исполнения: попытки принадлежат конкретному прогону.

Для этапа храним ключ, статус (`pending`, `queued`, `running`, `succeeded`, `failed`), номер попытки, время начала/окончания и ошибку. Артефакт привязан к прогону и успешной попытке этапа, имеет путь и хэш. События — журнал только на добавление.

1. Запуск создаёт прогон и этапы; в очередь отправляется только первый готовый этап.
2. Worker атомарно захватывает `queued` через условный UPDATE. Повторное сообщение не запускает уже захваченный этап.
3. После выполнения harness проверяет выход, фиксирует результат и ставит следующий этап в очередь.
4. Между фиксацией `queued` и публикацией сообщения возможен сбой. API периодически (раз в 10 секунд, один процесс API) повторно отправляет `queued`, которые не были захвачены за 30 секунд. Дубликаты безопасны благодаря условному захвату. Отдельный outbox в MVP не вводим.
5. Ошибку обычного этапа можно повторить вручную после завершения его задачи. Создаётся новая попытка; старые результаты сохраняются, следующие этапы не используют устаревшие артефакты.
6. Автоматически переотдавать `running` по lease в MVP не будем. После аварии worker оператор сначала останавливает worker, затем командой восстановления помечает незавершённый этап как failed и запускает новую попытку. Это исключает одновременную запись старого и нового исполнителя.

При завершении запись результата проверяет актуальный номер попытки. Перезапуск разрешён только для неактивного прогона. Повтор текущего failed-этапа — обязательная возможность; произвольный перезапуск с середины DAG и кэширование целых этапов отложены.

Все изменения кода и сборки внутри прогона последовательны. Один workspace не разделяется между параллельными агентами. Git-коммит можно делать после принятого этапа, но не после каждого `write`. Отдельные worktree на задачи понадобятся только при последующем включении параллельной разработки кода.

## 5. Шлюз модели и контекст

Все обращения проходят через одну внедряемую функцию:

```python
llm(*, system: str, user: dict, schema: dict) -> dict
```

Harness связывает её с текущими run/stage/attempt для учёта. Агент хранит свой системный промпт рядом с кодом и передаёт в `user` только данные задачи. Требования и приложенные тексты считаются недоверенными данными, а не инструкциями на запуск команд.

- Один HTTP-клиент, endpoint/model/ключ из окружения. Автоматического переключения провайдера нет.
- Проверка ответа по схеме обязательна. Структурированный вывод сервера используем только после проверки поддержки; иначе JSON + валидация и максимум одна починка.
- Для сетевых ошибок — максимум два повтора с паузой; у каждого запроса есть таймаут и предел выходных токенов. Бесконечных повторов и `xhigh` по умолчанию нет.
- Извлечение, форматирование и документация — без рассуждений или минимальный режим; сложные правила — по результатам замера. Неподдерживаемые сервером параметры не отправляем.
- Контекст собирает этап: роль, контракт выхода, конкретная задача, нужный срез спецификации и ошибки последней попытки. Историю всех этапов в запрос не вкладываем.
- При переполнении сокращаем примеры и посторонние части; если не помещается обязательный контракт — делим задачу или останавливаем её с объяснением. Молча обрезать требования нельзя.
- На прогон задаются лимиты времени, числа вызовов и токенов. При одном worker бюджет проверяется перед каждым запросом; исчерпание останавливает генерацию с частичным отчётом.

`llm_calls` записывается отдельно от транзакции результата этапа: начало вызова, завершение или ошибка, входные/выходные токены и рассуждения, если провайдер их сообщает, длительность. После сбоя расход может быть неизвестен — не записываем ноль и не придумываем точную стоимость. Секреты не попадают в артефакты и логи. Кэш ответов и Langfuse — последующие расширения.

## 6. Анализ, генерация и проверки

### Требования и допущения

Требования и критерии приёмки привязаны к исходному тексту. Техническое решение этап принимает самостоятельно. Небольшое бизнес-допущение записывается в ASM. Противоречие, меняющее результат или безопасность, не закрывается молча: MVP останавливается с понятным вопросом; менеджер исправляет требования и запускает новый прогон. Полный режим интерактивных вопросов и автоматические ответы по таймауту не строим.

### Генерация

Шаблон создаёт запуск, зависимости, Compose и основной CRUD. Модель пишет бизнес-логику. Сохраняем generation gap: генерируемые файлы и файлы модели лежат отдельно (`Generated`/`Hooks`/`Custom` или соответствующие каталоги frontend). Генератор не перезаписывает хуки. Нетиповые расширения ограничены явно разрешёнными путями.

Разработчик получает сигнатуры, BR, AC и ошибки проверки. Простейший цикл: сгенерировать реализацию → собрать/протестировать → до двух исправлений. Без универсального shell/tool-агента. Зависимости, CI и Compose модель напрямую не редактирует.

### Проверки

Тимофей готовит тесты из AC и публичных контрактов, не из реализации. Разработчик не может менять тесты ради зелёного результата. Ошибка теста исправляется отдельно с причиной и сохранением исходного результата; полноценный механизм споров — после MVP.

- Проверяем сборку, ключевое бизнес-правило на положительных, отрицательных и граничных примерах, запуск с БД, создание/чтение через API и один пользовательский сценарий в браузере.
- Не требуем, чтобы каждый тест падал на нейтральной заглушке: отрицательный пример может корректно пройти. Набор тестов должен ловить заведомо неверную реализацию правила. Для ключевого правила достаточно одной-двух осмысленных мутаций.
- Отдельно проверяем значение бизнес-параметра по исходному требованию. Ожидаемый результат не должен целиком вычисляться тем же кодом, что и реализация.
- Skipped и отсутствие проверки не считаются успехом. Тесты не удаляются в цикле ремонта.
- Версии зависимостей и lock-файлы закреплены в проверенном шаблоне. Находки безопасности записываются; блокирующие high/critical не замалчиваются и не подавляются автоматически. Полный набор SAST/DAST/fuzzing не является условием реализации первого сквозного прогона.

## 7. Запуск, Студия и итоговый отчёт

Студия использует существующий экран проектов: создать проект → запустить прогон → увидеть фактические статусы попыток, ошибку и артефакты → повторить failed-этап. Для MVP достаточно опроса API раз в 2 секунды. Redis pub/sub и SSE не нужны.

У каждого прогона свой `product/` и уникальный `COMPOSE_PROJECT_NAME`. Сборка и тесты — в заранее подготовленных контейнерах с фиксированными командами, ограничениями CPU/памяти и таймаутами. Доступ к Docker даётся только доверенному исполнителю; текст модели не становится shell-командой. Код продукта не получает секреты платформы.

Перед демонстрацией проверяем доступность модели, Docker, нужных образов и зависимостей. Одинаковые образы используем локально и в CI. Полную систему зеркал пакетов не строим. Первое доказательство работоспособности — локальный Compose и smoke; автоматический GitLab-деплой подключаем после этого, не блокируя независимую работу этапов.

Итоговый отчёт создаётся после проверок, а не параллельно с ними. В нём: что построено, статус каждого AC, результаты инструментов, допущения, ограничения, пути к приложению и логам, время, вызовы и токены. Таблицы и числа формирует код; LLM может писать только объясняющий текст. Если тесты или запуск не выполнены — это явно видно.

## 8. Разделение на пять независимых частей

| Участник | Владеет | Как проверяет независимо |
|---|---|---|
| Максим | Harness, run API, хранение, Celery/PostgreSQL, LLM-шлюз | Фиктивные этапы и HTTP-ответы модели; сценарии дубликата сообщения, потери публикации, ошибки и повторного запуска |
| Саня | `analysis`, `spec`, схемы их документов | Текст требований, заранее подготовленные ответы LLM, валидные и ошибочные документы |
| Артём | `ui`, Студия | Фиксированные analysis/app и подставные ответы модели; mock API запусков для frontend |
| Иван | `scaffold`, `develop`, шаблон продукта | Фиксированные app/ui, тестовый хук и ответы модели; сборка с нуля и повторная генерация без потери хука |
| Тимофей | `tests`, `verify`, `report` | Фиксированные контракты, правильная и заведомо неверная реализации, журналы успешного и неуспешного прогона |

Никто не ждёт готовности harness для написания своей функции. Контракты между частями фиксируем до начала параллельной разработки. Сборщик подключает функции к реестру этапов и проверяет сначала прогон с подставными ответами, затем два разных реальных бизнес-запроса. Успех первого домена не заменяет проверку второго.

Персональные промпты и инструкция интеграции добавляются отдельными файлами; до их фиксации этот документ задаёт архитектуру и границы MVP, а не полный контракт реализации.
