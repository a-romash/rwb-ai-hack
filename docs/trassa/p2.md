### 2.5 Неявные требования

**[Вывод]** Из постановки следуют семь требований, которые прямо не названы:

1. **Живой прогон скрытого кейса.** По умолчанию пайплайн работает автономно: вопросы закрываются допущениями, всё видно в отчёте. Он не зависит от интернета (зеркала пакетов, заранее собранные образы), укладывается в бюджет времени и честно показывает частичный результат.
2. **«Пригоден к развёртыванию на пользователей и дальнейшей поддержке».** Код — читаемый, на стандартной архитектуре, с тестами, README и runbook. Не «одноразовый прототип».
3. **«Универсальный конвейер».** Ни одного зашитого домена. Шаблоны делаются под класс приложений, а не под кейс.
4. **«Специализированный участок».** Каждая стадия запускается отдельно, например `trassa stage analyze case.pdf`. Если полный прогон сорвётся, команда всё равно показывает сильный компонент.
5. **«Минимизировать ручное вмешательство».** Число вмешательств — метрика отчёта. Цель в автономном режиме — 0.
6. **Модель событий, тестовые данные и документированный API** прямо требуются в кейсе №1. Значит, это обязательные выходы пайплайна для любого кейса.
7. **Интеграция через адаптер и mock-сервис.** Это стандартная возможность шаблона, а не частный случай парковок.

## 4. Анализ данных: spb.json и response.json

### 4.1 Что это за файлы

**[Факт]** Оба файла — ответы API одного формата: `{"result":"Success","message":"","data":{"city":…,"zones":[…]}}`. Код города в `spb.json` — `spb`, в `response.json` — `moscow_partner`. Поля зоны: `externalZoneId`, `displayName`, `geometry` (WKT), `price`, `priceDescription`, `minTime`, `timeStep`, `tariff{hasHolidays, periods[{from,to,duration,price,type}]}`, `entityState`, `initDate`, `lastSyncedAt`. Цифры ниже получены скриптом профилирования (приложение G).

**[Вывод]** Судя по полям `initDate`, `lastSyncedAt` и `entityState`, это выгрузка сервиса синхронизации с поставщиком парковочных данных. Ровно этот контракт должен отдавать mock-сервис поставщика, а адаптер — переводить его в доменную модель. Тогда замена mock на реального поставщика не затронет бизнес-логику, как и требует кейс.

### 4.3 Наблюдения и следствия

| # | Наблюдение [Факт] | Следствие [Вывод] |
|---|---|---|
| D1 | Зоны — **линии вдоль бордюра**, а не полигоны: 100% объектов в Петербурге и 98% в Москве. В Петербурге 5 объектов — GEOMETRYCOLLECTION из линии и вырожденной точки, 299 — MULTILINESTRING. В Москве 330 полигонов | «Машина в зоне» — это «расстояние до сегмента ≤ радиуса», а не «точка в полигоне». Нужны `ST_DWithin(geography, point, r)` с индексом GiST и нормализация геометрии через `ST_CollectionExtract(geom, 2)`. Для полигонов — отдельная ветка |
| D2 | **Высокая плотность.** В радиусе 20 м от середины сегмента — медиана 1 чужой сегмент (p90 — 3). В радиусе 50 м — медиана 3 (p90 — 6, максимум — 12). У 15,2% точек выборки в радиусе 50 м есть сегменты разных тарифов. Выборка — 600 сегментов | Погрешность GPS в застройке — десятки метров, поэтому однозначно выбрать сегмент по одной точке нельзя. Нужны ближайший сегмент, гистерезис, задержка по остановке (dwell) и показ альтернатив водителю |
| D3 | **Тарифная семантика.** `price` — копейки за час: в Петербурге 4 уровня, 100 / 200 / 280 / 360 ₽/ч. Пары периодов «`duration`=60» и «`duration`=null» (28 000 и 28 020) означают первый час по 280 ₽, дальше 4,67 ₽/мин, то есть 280,20 ₽/ч. В Москве `duration`=30 с ценой 10 000 и `null` с 15 000 соответствуют тексту «50 руб/30 мин, далее 150 руб/час» | Совпадает с публичными правилами Петербурга: 4 тарифа 100–360 ₽/ч, поминутная оплата со второго часа 1,67–6 ₽/мин (§5). Нужен тарифный движок с семантикой «начальный интервал + далее». Семантику фиксируем как допущение и задаём по ней вопрос |
| D4 | **Дней недели в структуре нет.** `from`/`to` — только минуты суток. Дни есть лишь в тексте: в Петербурге «пн-пт 08:00-20:00», в Москве «пн-сб» (3 928), «пн-вс» (3 993), без дней — 8 735 (из них «40 руб./час.» — 8 361) | Нужен детерминированный парсер описаний (регулярные выражения) со сверкой с периодами и допущение по умолчанию. Для `hasHolidays` нужен производственный календарь РФ |
| D5 | **Окна через полночь** в Москве: 1260→480, то есть 21:00–08:00, 16 024 периода | Интервалы с переходом через сутки. Проверяем тестами свойств |
| D6 | **Аномалии в Москве.** Зона 526131: `price` = 0 при ненулевом тарифе. 86 зон без периодов для легковых, в том числе 411520, хотя текст описывает тариф. 3 зоны с `hasHolidays`=false и текстом «Первые 2 часа - 0 руб., далее - 1000 руб./час»; у 411609 бесплатного интервала в структуре нет | Импорт с валидацией и карантином. Отчёт о качестве данных — артефакт анализа. Противоречия текста и структуры превращаются в вопросы |
| D7 | **Повторяющиеся адреса.** В Петербурге 1 232 значения `displayName` встречаются у нескольких сегментов. Рекорд — «пл. Тургенева 1», 20 сегментов | Зона идентифицируется по `externalZoneId`. В интерфейсе номер и адрес показываются вместе, поиск работает по номеру |
| D8 | **Официального номера зоны для оплаты в данных нет.** `externalZoneId` — шестизначный идентификатор сегмента у поставщика данных, а для оплаты по SMS нужен «номер парковочной зоны» (§5) | Вопрос аналитику. Допущение: показываем `externalZoneId` как номер зоны; адаптер поставщика может вернуть официальный номер |
| D9 | **Два города, разные правила:** `minTime` 60 и 30, окна через полночь, прогрессивные тарифы, полигоны | Модель не привязана к городу: город, часовой пояс и правила тарифа — это данные, а не код |
| D10 | **Объём:** 5,7 МБ и 11,4 МБ JSON — миллионы токенов. Файлы не помещаются в окно модели даже при 262k | Детерминированная стадия профилирования выдаёт карточку данных на 1–2 тыс. токенов. LLM видит статистику и 3–5 образцов, а не файл |

### 4.4 Карточка данных: что видит LLM вместо файла

Профилировщик пайплайна (стадия S0) работает без LLM и для любого табличного, JSON- или геонабора выдаёт компактную карточку. Пример для `spb.json`:

```yaml
dataset: spb.json            # путь к записям: data.zones[]
records: 6867
schema:
  externalZoneId: {type: string, unique: true, example: "517641"}
  displayName:    {type: string, values_shared_by_several_records: 1232}
  geometry:
    type: wkt
    kinds: {LINESTRING: 6563, MULTILINESTRING: 299, GEOMETRYCOLLECTION: 5}
    srid_guess: 4326
    bbox: [30.2298, 59.9091, 30.3999, 59.9787]
    linestring_length_m: {p50: 29.9, p95: 95.1, max: 514.9}
  price: {type: int, values: {36000: 2182, 28020: 2150, 20000: 1700, 10020: 835}}
  priceDescription: {type: text, distinct: 4, sample: "пн-пт 08:00-20:00, 280-280,2 ₽/час"}
  minTime: {const: 60}
  timeStep: {const: 15}
  tariff.hasHolidays: {const: true}
  tariff.periods: {per_record: 6, from_to: {"480-1200": 41202}, duration: {"null": 20601, "60": 20601},
                   type: {car: 13734, truck: 13734, bus: 13734}}
spatial:
  neighbours_within_20m: {p50: 1, p90: 3}
  neighbours_within_50m: {p50: 3, p90: 6, max: 12}
anomalies: []
semantics_to_confirm:
  - "price: копейки за час?"
  - "duration=60 — первый час, null — далее?"
  - "дни недели есть только в priceDescription"
samples: [3 записи, геометрия усечена]
```

**[Решение]** Карточка данных — пример контекст-инжиниринга (§11.4). Модель получает факты, на которых можно строить правила, и не тратит окно на сырой файл.

### 5.2 Что из этого следует для продукта

**[Вывод]**
- **«Требуется ли новая оплата»** — это функция от зоны, времени, дня недели, праздника, категории ТС, наличия активной сессии и момента «оплачено до». Её считает детерминированный тарифный движок, а не LLM при каждом запросе.
- **Два «окна вежливости» из правил города** — 15 минут на оплату и 10 минут на выезд — дают дополнительные уведомления к пяти обязательным из кейса. Пайплайн предлагает их как допущения со ссылкой на источник, а не вводит молча (§20.3).
- **Оплата привязана к номеру зоны.** Поэтому переезд в другую зону в платное время — повод проверить оплату. Формулировка кейса «Проверьте необходимость новой оплаты» оставляет решение водителю, и это правильно: агрегированные данные не гарантируют правил конкретной зоны.
- **Тариф зависит от категории ТС.** В профиле служебного автомобиля нужна категория, по умолчанию B (`car`).
- **Платёжный механизм не нужен.** Нужны переход в официальный сервис и mock-адаптер поставщика с заменяемой реализацией.

### 6.2 Профили контекста

Окно в инсталляции организаторов неизвестно, а по условию оно маленькое. **[Решение]** При старте шлюз опрашивает сервер: `GET /v1/models` (поле `max_model_len`) и пробные вызовы. По результату он выбирает профиль:

| Профиль | `max_model_len` | Вход на вызов, максимум | Резерв на ответ | Размышления |
|---|---:|---:|---:|---|
| XS | 8 192 | 5 000 | 2 000 | Выключены везде, кроме анализа: low, не больше 1 000 |
| S | 16 384 | 10 000 | 3 000 | low или medium в анализе, не больше 2 500 |
| **M (по умолчанию)** | 32 768 | 18 000 | 4 000 | medium в анализе и ремонте, не больше 6 000 |
| L | ≥ 65 536 | 24 000 — больше нарочно не берём | 6 000 | medium или high точечно |

Даже при большом окне мы его не заполняем. **[Факт]** Качество моделей падает с ростом длины входа неравномерно и даже на простых задачах; в исследовании Chroma 18 моделей, включая Qwen3 ([Chroma, Context Rot, 2025](https://trychroma.com/research/context-rot)). Информация в середине длинного контекста используется хуже, чем в начале и в конце ([Liu et al., Lost in the Middle](https://arxiv.org/abs/2307.03172)). Anthropic формулирует цель контекст-инжиниринга как «наименьший набор токенов с наибольшим сигналом» ([Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

### 6.3 Арифметика времени

**[Допущение]** Пусть прогон требует 150 тыс. **выходных** токенов. На одном потоке при 30 ток/с это около 83 минут. На серверном GPU при 8 параллельных запросах и суммарных 300–500 ток/с — 5–8 минут. Если же модель пишет приложение целиком (около 25 тыс. строк, то есть 300+ тыс. токенов) и чинит его длинными итерациями, прогон занимает часы.

**[Вывод]** Время прогона определяется выходными токенами и последовательностью вызовов. Отсюда три решения:
1. Модель пишет только «дыры».
2. Независимые задачи идут параллельно.
3. Рассуждения строго ограничены по бюджету.

### 6.4 Следствия для архитектуры

| # | Решение | Почему |
|---|---|---|
| 1 | Каждый вызов одноходовый и не хранит состояния: роль + задача + контекст-пакет. Истории диалога нет | Окно не растёт, ошибки не накапливаются (§8) |
| 2 | Контекст-пакеты собирает код по приоритетам, токены считает сервер (`/tokenize`) | Гарантированно не выходим за бюджет |
| 3 | Политика размышлений по стадиям, жёсткий `max_tokens`, обрыв рассуждений по бюджету | Защита от переразмышления (§6.1) |
| 4 | Данные — через JSON Schema с ограниченным декодированием; код — обычным текстом | Валидность структуры гарантирована; формат JSON ухудшает код (§8) |
| 5 | Декомпозиция до задач уровня функции или файла | Это сильная зона модели: LiveCodeBench, а не DeepSWE |
| 6 | Параллельные вызовы и стабильные префиксы промптов для кэша префиксов | Скорость (§11.9) |
| 7 | Опрос возможностей сервера при старте: окно, структурированный вывод, инструменты, переключение размышлений | Работаем с любой инсталляцией организаторов |
| 8 | Инструкции агентам — на английском, содержимое и тексты для людей — на русском | **[Допущение]** проверяем A/B-сравнением на eval-наборе (§11.14) |
| 9 | PDF-слайды разбираем текстом (PyMuPDF), vision включаем только для слайдов-картинок | Изображения дорого стоят по токенам |
