
## 14. Данные и PostGIS

### 14.1 Схема (эталон для кейса №1, фрагмент)

```sql
CREATE EXTENSION IF NOT EXISTS postgis;

-- Сегменты платной парковки (нормализованная геометрия + исходная запись для трассируемости)
CREATE TABLE parking_zone (
    id                uuid PRIMARY KEY,                 -- UUIDv7 генерирует приложение
    city              text        NOT NULL,             -- spb | moscow_partner | …
    external_id       text        NOT NULL,             -- externalZoneId поставщика
    display_name      text        NOT NULL,
    geom              geometry(Geometry, 4326) NOT NULL,-- LINESTRING | MULTILINESTRING | POLYGON
    geog              geography   NOT NULL,             -- для метров и индекса
    min_minutes       integer     NOT NULL,             -- minTime
    step_minutes      integer     NOT NULL,             -- timeStep
    free_on_holidays  boolean     NOT NULL,             -- hasHolidays (семантика — ASM)
    days_mask         smallint,                         -- биты пн…вс из парсера описания; NULL — неизвестно
    description       text,                             -- priceDescription
    quality_flags     text[]      NOT NULL DEFAULT '{}',
    raw               jsonb       NOT NULL,             -- исходная запись
    source_synced_at  timestamptz,
    is_active         boolean     NOT NULL DEFAULT true,
    UNIQUE (city, external_id)
);
CREATE INDEX ix_parking_zone_geog ON parking_zone USING gist (geog);

CREATE TABLE tariff_period (
    zone_id                 uuid     NOT NULL REFERENCES parking_zone (id) ON DELETE CASCADE,
    vehicle_type            text     NOT NULL,          -- car | truck | bus
    from_minute             smallint,                   -- NULL — весь день
    to_minute               smallint,                   -- from > to — через полночь
    first_minutes           smallint,                   -- NULL — «далее»
    rate_kopecks_per_hour   integer  NOT NULL
);
CREATE INDEX ix_tariff_period_zone ON tariff_period (zone_id, vehicle_type);

-- Телеметрия: идемпотентно по fix_id; BRIN по времени
CREATE TABLE location_fix (
    fix_id       uuid        PRIMARY KEY,
    vehicle_id   uuid        NOT NULL,
    recorded_at  timestamptz NOT NULL,
    position     geography(Point, 4326) NOT NULL,
    accuracy_m   real,
    speed_mps    real
);
CREATE INDEX ix_location_fix_vehicle_time ON location_fix (vehicle_id, recorded_at DESC);
CREATE INDEX brin_location_fix_time ON location_fix USING brin (recorded_at);

CREATE TABLE parking_session (
    id            uuid PRIMARY KEY,
    vehicle_id    uuid        NOT NULL,
    driver_id     uuid        NOT NULL,
    zone_id       uuid        NOT NULL REFERENCES parking_zone (id),
    status        text        NOT NULL,   -- SUGGESTED | UNPAID_WARNING | ACTIVE | EXPIRING | EXPIRED | CLOSED | CANCELLED
    started_at    timestamptz,
    paid_until    timestamptz,
    closed_at     timestamptz,
    close_reason  text,
    provider_ref  text,
    version       integer     NOT NULL DEFAULT 0          -- оптимистичная блокировка
);
-- не больше одной «живой» сессии на машину
CREATE UNIQUE INDEX ux_session_live ON parking_session (vehicle_id)
    WHERE status IN ('SUGGESTED', 'UNPAID_WARNING', 'ACTIVE', 'EXPIRING', 'EXPIRED');

-- Плюс: vehicle_zone_state, domain_event (история), notification, outbox_message, processed_message,
-- scheduled_job, audit_log, app_user, vehicle, driver, setting, import_run, import_quarantine
```

### 14.2 Импорт и качество данных

| Шаг | Что делается | Откуда требование |
|---|---|---|
| Разбор WKT | `WKTReader` из NetTopologySuite; SRID 4326 | D1 |
| Нормализация | GEOMETRYCOLLECTION → только линии (`ST_CollectionExtract(geom, 2)`); проверка `ST_IsValid`; расчёт `geog` | D1 |
| Тарифы | Периоды → `tariff_period` (копейки в час); `duration` → `first_minutes` | D3, D5 |
| Дни недели | Парсер `priceDescription`: «пн-пт», «пн-сб», «пн-вс», «кроме праздников», варианты написания «с» и «c» → `days_mask`; нет совпадения → `NULL` + флаг | D4 |
| Сверка текста и структуры | «Первые 2 часа - 0 руб.» ↔ период `first_minutes=120, rate=0`; верхнеуровневый `price` ↔ ставки car | D6 |
| Карантин | Нет геометрии или тарифа для car → `import_quarantine`; противоречия → импорт с `quality_flags` | D6 |
| Идемпотентность | Upsert по `(city, external_id)`; зоны, исчезнувшие из выгрузки, → `is_active=false` | Синхронизация |
| Отчёт | `docs/data/data-quality.md`: счётчики, флаги, примеры | Качество анализа |

### 14.3 Геозапросы и производительность

- **«Рядом»** — `ST_DWithin` по `geography` + KNN `<->` (§12.5). Интеграционный тест выполняет `EXPLAIN (FORMAT JSON)` и проверяет, что используется индекс `ix_parking_zone_geog`. Индекс проверяется тестом, а не на словах.
- **«Есть ли платная зона рядом»** — тот же запрос с `LIMIT 1`. Полигоны района для детектора не нужны.
- **Граница «зоны платной парковки» на карте** — объединение буферов сегментов, рассчитывается при импорте для отображения.
- **Тайлы** — `ST_AsMVT` с `ST_AsMVTGeom(ST_Transform(geom, 3857), ST_TileEnvelope(z, x, y))`. Ответ кэшируется: зоны меняются редко.
- **НФТ [Допущение — замерить]:**
  - поиск ближайших зон — p95 ≤ 20 мс на 23,5 тыс. сегментов;
  - обработка точки телеметрии от приёма до события — p95 ≤ 2 с;
  - уведомление водителю — не позже 10 с после события.

### 14.4 Персональные данные

- **[Факт]** Ч. 5 ст. 18 152-ФЗ требует хранить и обрабатывать персональные данные граждан РФ в базах данных на территории РФ ([КонсультантПлюс](https://www.consultant.ru/document/cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/)).
- **[Вывод]** Геопозиция идентифицируемого сотрудника — персональные данные. Отсюда меры:
  - **цель и согласие:** контроль парковки служебного ТС во время смены; согласие на экране онбординга;
  - **трекинг** только во время смены;
  - **хранение** сырых точек — 30 дней, сессий — 1 год [Допущение];
  - **доступ:** водитель видит только свои данные, диспетчер — автопарк;
  - **логи** без координат;
  - **размещение** — в контуре компании;
  - **демо** — на синтетических водителях и машинах.

## 15. Модель событий и интеграции

### 15.1 Топики Kafka (эталон для кейса №1)

| Топик | Ключ | Производитель | Потребители | Хранение | События |
|---|---|---|---|---|---|
| `fleet.telemetry.v1` | `vehicleId` | API | Geofencing (Worker) | 24 ч | `LocationFixReceived` |
| `parking.zone-events.v1` | `vehicleId` | Worker через outbox | Sessions, Notifications, AdminFeed, History | 7 дней | `PaidAreaEntered`, `PaidAreaLeft`, `ZoneEntered`, `ZoneLeft`, `ZoneChanged` |
| `parking.session-events.v1` | `vehicleId` | API и Worker через outbox | Notifications, AdminFeed, History | 7 дней | `SessionSuggested`, `UnpaidStopWarning`, `SessionStarted`, `SessionExtended`, `SessionExpiringSoon`, `SessionExpired`, `SessionGraceEnded`, `SessionClosed`, `PaymentCheckRequired` |
| `notifications.v1` | `userId` | Worker | SSE-шлюз в API | 3 дня | `NotificationCreated` |
| `<topic>.dlq` | Исходный | Консьюмеры | Оператор | 14 дней | Сообщения, которые не удалось обработать |

**Почему ключ — `vehicleId`.** Все события одной машины попадают в одну партицию, поэтому их порядок внутри топика гарантирован. Порядок между топиками обеспечивает причинность: события сессий рождаются при обработке событий зон.

### 15.3 Гарантии

| Гарантия | Механизм |
|---|---|
| Состояние и событие атомарны | Transactional outbox: изменение и строка `outbox_message` пишутся в одной транзакции. Публикатор читает пачки через `FOR UPDATE SKIP LOCKED`, продюсер работает с `enable.idempotence=true` и `acks=all` |
| Доставка | At-least-once. Идемпотентность консьюмера: `processed_message(consumer, event_id)` пишется в той же транзакции, что и эффект |
| Ошибки | 3 повтора с задержкой → DLQ; метрика и событие в журнал администратора |
| Порядок | По ключу внутри топика; партиция обрабатывается последовательно |
| Эволюция схем | Внутри `v1` только добавление полей. Ломающее изменение → `v2` топика и типа. Схемы описаны в AsyncAPI, контрактные тесты проверяют каждый произведённый payload |
| Время | `time` — доменное время из `TimeProvider`, а не таймстамп Kafka |

### 15.4 Документирование

- **AsyncAPI 3.0** генерируется из IR: каналы, операции send и receive, сообщения с JSON Schema, Kafka-биндинги с ключом. Из него собирается HTML для `docs/` средствами генератора AsyncAPI в node-образе.
- **OpenAPI 3.1** отдаёт сам бэкенд (`/openapi/v1.json`), Scalar показывает его на стенде. Статичная копия кладётся в `docs/`.
- **В профиле `demo`** Kafka UI показывает жюри живые топики. Модель событий видна, а не только описана.

## 16. Тестирование и безопасность

### 16.1 Пирамида тестов генерируемого продукта

| Уровень | Инструменты | Что проверяет | Пример из кейса №1 | Кто пишет | Объём, цель |
|---|---|---|---|---|---:|
| Unit и свойства | xUnit, FsCheck | Правила, тарифы, детектор, машины состояний | `IsPaidNow` на границах 07:59, 08:00, 19:59 и 20:00, в выходные и праздники; детектор без «дребезга» при шуме ±20 м | QA по AC + генератор (свойства машин состояний) | 120–200 |
| Интеграционные | WebApplicationFactory + PostGIS + Kafka | API, БД, события, индексы | Телеметрия → `ZoneEntered` в топике; `EXPLAIN` использует GiST | QA + шаблон | 25–40 |
| Контрактные | JSON Schema событий, WireMock.Net, Schemathesis | Соответствие контрактам, устойчивость API | Payload `ZoneChanged` соответствует AsyncAPI; адаптер переживает 5xx | Генератор + QA | 10–20 + fuzzing |
| UI веб | Jest + Testing Library | Фасад, «дыры» UI | Таймлайн сессии | Шаблон + QA | 30–60 |
| UI мобильный | Robolectric + Compose testing, Turbine | Экраны, ViewModel | «Оплачено до 15:20», «осталось 10 минут» | QA | 20–40 |
| E2E веб | Playwright + axe | Сценарии ролей на стенде | Диспетчер видит событие смены зоны в живой ленте | QA | 8–15 |
| Сценарный (демо) | Драйвер маршрута + `FakeTimeProvider` | Все 9 шагов демо как один тест | §20.6 | Генератор из IR + QA | 1 + варианты |
| Мутационное (расширение) | Stryker.NET | Качество тестов правил | Доля убитых мутантов по BR | — | По бюджету времени |

### 16.2 Правила независимости

1. **Агент QA видит:** AC с примерами, OpenAPI, AsyncAPI, page objects, тестовый DSL и драйверы. **Реализацию не видит никогда.**
2. **Red-proof (G2).** Тест бизнес-правила обязан упасть на каркасе с заглушками. Тест, который проходит на каркасе, возвращается автору.
3. **Неизменность.** `tests/` и `spec/` смонтированы для разработчиков только на чтение, хэши сверяются после S4.
4. **Пропуск не равен успеху.** Skipped, xfail и ignored в паспорте считаются непройденными.
5. **Число тестов** между итерациями не уменьшается без новой версии спецификации.
6. **Маркировка AC:** xUnit `[Trait("AC", "AC-07")]`, Playwright — заголовок `@AC-07 …`, Kotlin — имя метода `AC_07_…`. Парсеры отчётов строят матрицу «AC → тест → результат».
7. **Связь «AC → код» измеряется.** Приёмочные тесты прогоняются отдельно по каждому AC с фильтром (`dotnet test --filter "AC=AC-07"`) и сбором покрытия. Строки, исполненные тестами AC, и есть связь, а не комментарий агента.

### 16.4 Модель угроз кейса №1 (STRIDE, фрагмент)

| Угроза | Сценарий | Мера |
|---|---|---|
| Spoofing | Телеметрия от имени чужой машины | JWT; `vehicleId` берётся из токена водителя, а не из тела запроса |
| Tampering | Подмена «оплачено до» | Только через подтверждение поставщика или явную отметку водителя; всё пишется в аудит |
| Repudiation | «Я не продлевал» | Append-only журнал действий |
| Information disclosure | Чужие треки (IDOR) | Авторизация на уровне ресурса; тесты IDOR; логи без координат; TLS на прокси стенда |
| Denial of service | Флуд телеметрии | Rate limit на устройство, лимит размера пачки, обратное давление Kafka |
| Elevation of privilege | Водитель вызывает методы администратора | Политики на группах эндпоинтов из матрицы RBAC; тесты |
| Мобильное приложение | Секреты в APK, перехват трафика | Секретов в APK нет; network security config разрешает cleartext только для локального dev-хоста; токен зашифрован ключом Android Keystore |
| Цепочка поставок | Вредоносный или галлюцинированный пакет | Allowlist, lock-файлы, зеркала, SBOM, лицензии |
| Персональные данные | Избыточный сбор и хранение | Трекинг только в смену, сроки хранения, согласие, размещение в РФ (§14.4) |

A10 Mishandling of Exceptional Conditions — ProblemDetails без стектрейсов и тестами путей ошибок ([OWASP Top 10:2025](https://owasp.org/Top10/2025/ja/)).
- **OWASP ASVS 5.0.** Чек-лист уровня L1 генерируется из IR: аутентификация, сессии, авторизация, валидация, API, журналирование, защита данных, конфигурация. Каждый пункт ссылается на тест или проверку.
