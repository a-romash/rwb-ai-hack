
## 17. Инфраструктура и CI/CD

### 17.1 Два окружения

| Окружение | Состав | Как поднимается |
|---|---|---|
| **Платформа «Трасса»** | `trassa-api` (FastAPI), `trassa-worker` (оркестратор), `trassa-studio` (nginx + сборка Angular), SQLite по умолчанию или PostgreSQL. Через `docker-socket-proxy` с ограниченным набором методов оркестратор управляет контейнерами песочницы. Профиль `llm` — локальный vLLM при наличии GPU. Профиль `offline` — зеркала Verdaccio (npm), BaGet (NuGet), Reposilite (Maven) | `make up` или `docker compose up -d`. Первым делом `trassa doctor` |
| **Сгенерированный продукт** | PostgreSQL + PostGIS, Kafka (KRaft), API, Worker, admin (nginx). Профиль `demo`: provider-mock, симулятор, Kafka UI. Одноразовая задача миграций и импорта | `docker compose up -d` из `deploy/` — локально, на стенде или в CI |

**[Решение]** Доступ к Docker есть только у оркестратора, и только через socket-proxy. Агенты не получают ни Docker, ни сети (§11.12).

### 17.2 Образы инструментов

Образы собираются заранее и лежат в registry локального GitLab:

| Образ | Содержимое | Что прогрето |
|---|---|---|
| `trassa/tool-dotnet:10` | .NET SDK 10.0.x, dotnet-ef | Кэш NuGet по `Directory.Packages.props` шаблона |
| `trassa/tool-node:22-ng20.1.6` | Node 22 LTS, Angular CLI 20.1.6, Playwright + Chromium, openapi-generator (JRE), генератор AsyncAPI | Кэш npm по lock-файлу шаблона, браузеры Playwright |
| `trassa/tool-android` | JDK 17, Android SDK (compileSdk и targetSdk закреплены в шаблоне), Gradle, зависимости Kotlin 2.2.21 | Кэш Gradle: сборка шаблона проходит с `--offline` |
| `trassa/tool-security` | Semgrep и локальные правила, gitleaks, Trivy со снимком БД уязвимостей, hadolint, Schemathesis | Базы для работы без сети |
| `zaproxy` (официальный образ) | ZAP baseline | Скачан заранее |
| `trassa/tool-docs` | MkDocs Material, плагин mermaid, pandoc (ТЗ в DOCX) | Плагины установлены, сборка без сети |

### 17.3 GitLab CI генерируемого продукта

Пайплайн генерирует `.gitlab-ci.yml` из шаблона под включённые компоненты. Скелет — в [приложении D](#приложение-d-скелет-gitlab-ciyml-генерируемого-продукта).

| Стадия | Задачи | Особенности |
|---|---|---|
| `lint` | `backend:format`, `admin:lint`, `mobile:lint` (detekt, ktlint, Android Lint) | `rules: changes` по папке компонента |
| `build` | `backend:build`, `admin:build`, `mobile:assemble` (APK — артефакт) | Кэш по lock-файлам |
| `test` | `backend:test` (unit, архитектура, интеграционные — с `services:` PostGIS и Kafka), `admin:test` (Jest), `mobile:test` (Robolectric) | Отчёты `junit` и `coverage_report: cobertura` |
| `security` | `sec:sast` (Semgrep), `sec:secrets` (gitleaks), `sec:deps-licenses` (Trivy fs), `sec:config` (Trivy config + hadolint), `sec:sbom` | Артефакты SARIF и JSON; гейт — скрипт-политика по §16.3 |
| `package` | `package:images` (DinD или Buildah → registry), `sec:container` (Trivy image) | Kaniko не используем (§2.4) |
| `deploy` | `deploy:demo` — `docker compose up -d` на хосте стенда через раннер с тегом `demo` | `environment: {name: demo, url: …}` |
| `verify` | `verify:smoke`, `verify:e2e` (Playwright по стенду), `verify:scenario` (сценарий демо), `verify:dast` (ZAP baseline), `verify:fuzz` (Schemathesis) | Снимки экранов — артефакты |
| `docs` | `docs:build` (MkDocs → артефакт или Pages) | Снимки берутся из `verify` |

**Используемые возможности GitLab:**
- `needs` для DAG: компоненты собираются и тестируются параллельно;
- `interruptible`;
- `retry` только при `runner_system_failure`;
- явные `timeout`;
- `cache:key:files` по lock-файлам;
- `artifacts:reports` для тестов и покрытия;
- `environment` для стенда.

**[Решение]** Сканеры безопасности запускаем своими задачами из `tool-security`, а не шаблонами GitLab. Шаблоны тянут образы анализаторов из внешнего registry, а результат должен быть одинаковым при любом тарифе GitLab и без интернета.

### 17.4 Раннеры и стенд

- **Docker executor** с privileged DinD для сборки образов. Если privileged запрещён — Buildah.
- **Shell-раннер с тегом `demo`** на хосте стенда для деплоя.
- Параллельность — 4 задачи, общий том кэша.
- **Стенд** — Docker host. Каждый продукт поднимается со своим `COMPOSE_PROJECT_NAME`, чтобы прогоны не мешали друг другу. Обратный прокси раздаёт поддомены или порты.

### 17.5 Готовность к оценке без интернета

Команда `trassa doctor` проверяет и печатает зелёный или красный список:

- [ ] API GitLab и токен, права на группу `trassa-runs`;
- [ ] registry — образы инструментов на месте;
- [ ] раннеры — `docker`, `demo` — онлайн;
- [ ] эндпоинт модели: `max_model_len`, структурированный вывод, выключение размышлений, пропускная способность;
- [ ] зеркала пакетов — сборка шаблонов с `--offline` проходит;
- [ ] снимок БД Trivy не старше N дней;
- [ ] свободное место на диске, синхронизация времени, DNS стенда.

**[Вывод]** Половина рисков живого прогона — инфраструктурные. Команда, которая за 30 секунд показывает «всё зелёное» до запуска, выигрывает доверие жюри ещё до демо.

## 18. Документация

### 18.1 Что выпускает пайплайн

Типы документов размечены по Diátaxis: учебник, инструкция, справочник, объяснение.

| Комплект | Документы | Источник |
|---|---|---|
| **Продуктовый** | `vision.md` (проблема, пользователи, ценность, объём), `personas-roles.md`, `user-stories.md`, `acceptance-criteria.md` (Gherkin), `assumptions-decisions.md` (ASM и решения), `glossary.md` | IR: `requirements`, `quality` |
| **Системный** | `requirements.md` (REQ, ISS, Q, ASM), `architecture.md` (C4 L1–L3 в mermaid), `adr/*.md`, `domain-model.md`, `state-machines.md`, `events.md` + AsyncAPI HTML, `api.md` + статический OpenAPI, `database.md` (таблицы из миграций), `integrations.md` (порты, адаптеры, поведение mock), `nfr.md` (как проверено), `security.md` (модель угроз, чек-лист ASVS, результаты сканеров), `testing.md` (стратегия и результаты), `traceability.md` (матрица REQ → BR → AC → тест → код → документ), `data/data-quality.md` | IR + отчёты гейтов + покрытие |
| **Пользовательский** | `driver-guide.md` (снимки Roborazzi), `dispatcher-guide.md` и `admin-guide.md` (снимки Playwright), `notifications.md` (все тексты и когда они приходят), `faq.md` | UI-IR, `copy.yaml`, снимки из тестов |
| **Эксплуатационный** | `README.md` (быстрый старт), `runbook.md` (деплой, конфигурация, переменные окружения, логи, диагностика, резервное копирование, ротация секретов), `ci-cd.md` | Шаблоны + IR `delivery` |
| **По ГОСТ** (опция) | ТЗ в структуре ГОСТ 34.602-2020 → DOCX через pandoc | IR — те же данные в другой форме |
| **Отчёты** | `reports/passport.md` и HTML; `reports/run-<id>/report.md` — эффективность | Журнал прогона |

### 18.2 Как генерируется

- **Детерминированно:** таблицы, диаграммы, матрицы, справочники API и событий, списки требований. Это около 70% объёма документации, 0 токенов.
- **LLM пишет связный текст разделов.** В пакет попадают только факты раздела: элементы IR, результаты тестов, числа из паспорта, до 1,5 тыс. токенов. Разделы пишутся параллельно.
- **Снимки экранов** — только из реальных тестовых прогонов: Playwright на стенде, Roborazzi на JVM. Рисованных макетов в пользовательской документации нет.
- **Сайт документации** — MkDocs Material с mermaid, собирается в CI без интернета.

### 18.3 Проверки документации

- Каждый AC упомянут в системной и пользовательской документации, где это уместно.
- У каждого экрана есть снимок.
- Битых ссылок нет: проверка в офлайн-режиме.
- markdownlint чистый, нет «TODO» и «lorem».
- Числа в тексте совпадают с паспортом: шаблон подставляет их из одного источника.

## 19. Отчёт о токенах, времени и попытках

### 19.1 Где и в каком виде

- `reports/run-<id>/metrics.json` — машиночитаемый.
- `reports/run-<id>/report.md` — для людей.
- Экран «Эффективность» в Studio.
- Сводка в описании MR.

Все числа считаются **из журнала вызовов и событий**, а не со слов агентов.

### 19.2 Журнал вызова LLM

```json
{
  "run_id": "20261030-1200-7f3a",
  "call_id": "c-000137",
  "stage": "S4",
  "agent": "backend_dev",
  "task_id": "hole:BR-04.is-paid-now",
  "attempt": 2,
  "prompt_version": "backend_dev@1.4.0",
  "context_profile": "M",
  "thinking": "off",
  "tokens": { "prompt": 6120, "cached_prompt": 3584, "completion": 412, "reasoning": 0 },
  "latency_ms": { "ttft": 380, "total": 5210 },
  "outcome": "compile_error",
  "pack_sections": { "role": 820, "cheatsheet": 1040, "contract": 300, "task": 210,
                     "ir": 1650, "signatures": 1380, "examples": 0, "repair": 720 }
}
```

`cached_prompt` заполняется, если сервер отдаёт `prompt_tokens_details.cached_tokens`; в vLLM это включается отдельным флагом. Запуски инструментов — сборки, тесты, сканеры — пишутся отдельно: длительность, результат, код выхода.

### 19.3 Структура отчёта

*Значения ниже — пример формата, а не замер.*

| Блок | Содержимое |
|---|---|
| Сводка | Общее время прогона; машинное время LLM и инструментов; токены (вход, из кэша, выход, размышления); вызовы; попытки; ручные вмешательства; итог — AC зелёные из общего числа |
| По стадиям | Таблица S0…S8: время, вызовы, токены, попытки, результат гейта |
| По агентам | Таблица: вызовы, токены, доля успешных с первой попытки |
| По задачам | Топ-10 самых дорогих задач; распределение попыток по «дырам»: с первой попытки, после ремонта, заглушено |
| Эффективность | Доля детерминированного кода; доля попаданий в кэш префиксов; средняя параллельность; токены и время на один AC |
| Сравнение | Дельты с прошлым прогоном того же кейса |
| Методика | Где и как измерено, что не учтено |

Пример строки «По стадиям»:

| Стадия | Время | Вызовов | Вход, тыс. | Из кэша, тыс. | Выход, тыс. | Размышления, тыс. | Попыток | Гейт |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| S2 Системный анализ | 6 мин 40 с | 21 | 182,3 | 71,0 | 24,1 | 9,1 | 23 | G1 ✅ |

### 19.4 Формулы

- **Доля детерминированного кода** = строки вне маркеров «дыр» / все строки сгенерированного кода. Маркеры дают точный учёт.
- **Попыток на «дыру»** = Σ попыток / число «дыр».
- **First-pass rate** = «дыры», закрытые с первой попытки / все «дыры».
- **Ручные вмешательства** = число действий человека (ответы, утверждения, правки) в `run_events`.
- **Токенов на AC** = Σ токенов прогона / число AC в спецификации.
- **Стоимость** (опционально) = GPU-часы × ставка. Ставку задаёт владелец инфраструктуры.
