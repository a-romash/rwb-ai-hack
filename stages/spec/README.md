# Анализ требований и системный анализ

Реализованы S1–S6 и инструмент оценки S7. Фактические результаты настоящей модели находятся в [EVAL.md](EVAL.md), записанные регрессионные прогоны — в [EVAL-recorded.md](EVAL-recorded.md). Статус `partial` означает наличие нерешённых проблем и флагов, а не успешную реализацию всех требований.

## Установка и проверки

Нужен Python 3.12. Все прямые и транзитивные зависимости закреплены в `stages/analysis/requirements.txt` и `stages/spec/requirements.txt`.

```sh
# из корня репозитория
python3.12 -m venv .venv
.venv/bin/python -m pip install -r stages/analysis/requirements.txt
.venv/bin/python -m contracts.export
.venv/bin/python -m unittest discover -s stages/analysis/tests -v
.venv/bin/python -m unittest discover -s stages/spec/tests -v
.venv/bin/python -m unittest discover -s gates/tests -v
.venv/bin/python -m pip check
```


Зависимости перечислены отдельно; сетевой eval использует стандартную библиотеку Python:

## Независимый запуск

```sh
.venv/bin/python -m stages.spec.eval --mode recorded
.venv/bin/python -m stages.spec.eval --mode live
```

По умолчанию recorded проверяет две вручную подготовленные фикстуры; live — все три текста. Отсутствующая запись при явном выборе `--mode recorded --cases case1` считается отдельным неуспешным статусом, а не пройденной проверкой.

Для live-режима `.env` в корне содержит `OPENROUTER_API_KEY`. По умолчанию используется `qwen/qwen3.8-27b`. Для совместимого локального сервера можно задать `LLM_BASE_URL`, `OPENAI_API_KEY` и `--model`. Секреты не записываются в результаты.

Можно ограничить набор или выбрать иной исходный текст кейса №1:

```sh
.venv/bin/python -m stages.spec.eval --mode live --cases tickets equipment
.venv/bin/python -m stages.spec.eval --mode live --cases case1 --case1 stages/spec/eval/case1/requirements.md
```

Для сравнения прогонов используйте отдельный `--output stages/spec/EVAL-comparison.md`. Каждый запуск получает новую папку в игнорируемом `workspaces/eval/`. В ней сохраняются артефакты, выходы модели и `reports/eval.json` с фактическими вызовами, токенами, временем, находками и флагами. Повторное использование непустой рабочей папки отвергается. В eval явно различаются принятые и промежуточные артефакты.

## Подключение к дирижёру

Публичные функции соответствуют §3.2–3.3 задания:

```python
from stages.analysis import execute as analyze, repair as repair_analysis
from stages.spec import execute as specify, repair as repair_spec
from gates.g0_inputs import check as check_g0
from gates.g1_spec import check as check_g1
```

`execute(inp, workspace, llm, sandbox)` принимает зависимости извне. Эти этапы никогда не вызывают песочницу, HTTP API платформы или очередь. `repair(inp, workspace, llm, findings)` принимает только адресные JSON Patch; отклонённый патч не меняет исходный артефакт. Не больше двух кругов ремонта запускает дирижёр; такой же предел реализован в независимом eval.

Если `contracts.stage` и `contracts.gates` доступны, `stages.analysis.compat` импортирует их. Пока этих файлов нет, используются локальные дублёры по документу. `stages.analysis.testing` содержит независимые `FakeLLM`, `FakeSandbox` и `run_stage_locally`; чужой `harness/` не изменён. Тесты не требуют токена или доступа к сети.

В A0/A1 анализ возвращает вопросы и сохраняет контрольную точку. Следующий вызов с `answers` продолжает синтез без повторного извлечения источников. Частичные ответы сохраняются; ответы к изменившимся источникам отвергаются. A2 закрывает вопросы ответами по умолчанию и записывает ASM с требованием подтверждения.

## Артефакты и границы

- Принятые контрактные артефакты: `spec/analysis.json`, `spec/app.json`.
- Служебный паспорт `spec/analysis-inputs.json`: статусы файлов, проверенные фрагменты, шум и карточки данных. Добавлен отдельным артефактом `analysis_inputs`, без новых полей в общем `analysis.json`.
- `spec/analysis-checkpoint.json`: продолжение A0/A1 и подпись входа.
- `spec/spec-notes.json`: заметки и допущения стадии spec с указанием этапа; общий контракт анализа не меняется.
- Промежуточные JSON сохраняются после узких шагов для диагностики инфраструктурного сбоя; факт наличия файла не означает принятие этапа.
- Схемы разделов приложения, не описанных внутри §3.6, по-прежнему используют JSON-контейнеры. Их формат не объявляется согласованным контрактом команды.
- Гейты не вызывают модель или сеть и не меняют файлы. G1 содержит 18 семантических валидаторов плюс отдельную проверку `CONTRACT_APP`; вместе это 19 кодов. G0 содержит четыре кода.
- Проверка пересечения произвольных хуков консервативна и выдаёт предупреждение, если непересекаемость не доказана. Имена неявных событий поддерживают соглашения примеров документа; окончательное соглашение принадлежит генератору Ивана.
- Нормализация Gherkin исправляет только двоеточие после ключевого слова шага. Условия и ожидаемые результаты она не дописывает.
- Контекст каждого запроса собирается отдельно и проверяется вместе со схемой по консервативной оценке UTF-8-байтами. При разбиении требований и спецификации сохраняются стабильные ID. История диалога не передаётся.
- Если один элемент даже после разбиения не помещается, возвращается частичный артефакт с причиной ограничения окна. Бюджет eval резервирует вход и выход до обращения к провайдеру; ранние результаты до этого исправления могли немного превышать целевой бюджет, их фактический расход не исправляется задним числом.
- Из наборов данных модель получает только карточки; чтение сырых JSON/CSV/GeoJSON выполняет код. Карточка ограничена 7000 UTF-8 байтами, длинные примеры сокращаются. Если даже сводка всех полей не помещается, файл честно помечается неразобранным.

## Проверка готовности

Результаты тестов и команд сохранены в [TESTS.md](TESTS.md). Полная выдача по задачам S1–S7 и сырые логи eval удалены из репозитория ради размера: они остались в истории git (коммит `46c32a9`).

S7 выполняется на настоящем `qwen/qwen3.8-27b`: `tickets`, `equipment` и текст слайдов 13–17 из предоставленной презентации. Нормализованный текст и происхождение сохранены в `eval/case1/`. Полное описание кейса использовано для сверки порядка сценария; отдельные исходные наборы данных кейса не предоставлены, поэтому их свойства в этом прогоне не проверены. История неуспешных попыток и затраты разработки — в истории git (`stages/spec/eval-history/` до очистки).

Все оставшиеся ошибки гейтов должны быть видимы в EVAL и иметь флаги; `partial` допускается постановкой, но требует последующего разбора перед использованием спецификации. Согласование с платформой и фактическое использование фикстур коллегами остаются межкомандной интеграцией.

## Запрос владельцу

1. **Максиму:** предоставить общие `contracts.stage`, `contracts.gates`, `harness.fakes` и зарегистрировать наши `execute`/`repair`/`check` в дирижёре. Причина: эти файлы и механизм заморозки/очередей относятся к платформе; здесь реализована только независимая граница интеграции.
2. **Максиму и потребителям:** согласовать вспомогательные артефакты `analysis_inputs` и `spec_notes`, а также каноническое представление неразобранных входов, шума, связи NFR → REQ и допущений spec в будущей версии общего контракта. Причина: в v1 эти поля не определены; общий JSON не расширен самовольно.
3. **Ивану и потребителям:** закрепить модели открытых разделов, грамматику фильтров/эффектов, политику owner/own для разных ролей и точное образование событий переходов. Причина: без контракта генератора соответствующие проверки остаются ограниченными и консервативными.
4. **Артёму:** проверить подключение `StageOutput.questions` и возобновление через `answers` в Студии. Причина: UI ожидания принадлежит его части и здесь не менялся.
