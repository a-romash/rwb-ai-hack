# Контракт Студии с API

Какие эндпоинты использует фронтенд, как он трактует ответы и что ему нужно от бэкенда дальше.

## Используется сейчас

| Метод и путь | Где в Студии | Как используется |
|---|---|---|
| `GET /api/health` | Индикатор «API на связи» в шапке | Опрос раз в 20 секунд, при ошибке — раз в 6 секунд; на скрытой вкладке опрос на паузе |
| `GET /api/projects` | Список проектов, командная палитра | Сортировка «Недавние» берётся из ответа, «По названию» считается на клиенте |
| `POST /api/projects` | Новый проект | Тело `{name, requirements}`; после 201 — переход в `/projects/:id/flow` |
| `GET /api/projects/{id}` | Рабочая область | Название и требования. Этапы проекта показываются участниками шагов конвейера RWB |
| `PATCH /api/projects/{id}` | Переименование, сохранение требований | Отправляется только изменённое поле |
| `POST /api/projects/{id}/jobs` | Диалог запуска агента | `{agent, prompt}`; `prompt` — инструкция этапа плюс требования. Без инструкции поле не передаётся, и бэкенд берёт требования проекта |
| `GET /api/projects/{id}/jobs/{job_id}` | Вкладка «Запуски», станции на линии | Опрос: 1,5 с в первые 30 с, потом 3 с, после 3 минут — 6 с. После 20 минут в `pending` задача помечается «Нет статуса» |

### Как читается статус задачи

| `status` | `subtype` | Студия показывает |
|---|---|---|
| `queued`, `pending`, `received` | — | В очереди |
| `started`, `retry` | — | Выполняется |
| `success` | `success` | Готово |
| `success` | `partial`, `budget` | Частично, бюджет исчерпан |
| `success` | `blocked` | Нужен ответ |
| `success` | `error`, `error_max_turns`, `unfinished`, `no_progress` | Ошибка (задача в очереди прошла, а агент — нет) |
| `failure` | — | Сбой задачи |
| `revoked` | — | Отменено |

Celery возвращает `pending` и для неизвестной задачи. Поэтому после истечения результата (`result_expires = 3600`) Студия не откатывает готовый статус и показывает сохранённый результат.

## Что нужно от бэкенда дальше

Фронтенд уже готов показать эти данные: поля в `src/app/core/api/api.types.ts` необязательны, и интерфейс включает блоки, когда они приходят.

1. **Расширить `JobRead`** полями, которые харнесс уже считает (`backend/app/tasks.py`, `_PUBLIC`): `usage` (токены, рассуждения, кэш, попытки), `duration_ms`, `assumptions`. Карточка запуска покажет расход и допущения агента; это закрывает отчёт о токенах, времени и попытках из требований кейса.
2. **Список задач проекта** `GET /api/projects/{id}/jobs`. Сейчас история запусков хранится в браузере, и другой пользователь её не видит.
3. **Маршруты прогонов по контракту M0** (`contracts/api.py`): `RunRead` со шагами, бюджетом и автономией, `StageRunRead.gate` для ворот, `AnswersCreate` и `GateDecisionCreate`. Таймлайн конвейера уже построен на ключах `harness/registry.py`: статусы шагов и результаты ворот подставятся без правок вёрстки.
4. **Поток событий прогона** по SSE, например `GET /api/runs/{id}/events`. nginx уже проксирует `/api/` без буферизации и с часовым таймаутом чтения.
5. **Ответ на вопросы агента** (`blocked`, `waiting_input`): эндпоинт для ответа аналитика. В карточке уже есть статус «Нужен ответ».
